# 项目开发路线图

## 1. 使用方式

本路线图定义长期开发阶段、任务 ID、依赖、产物和验收标准。

- 实时状态以 `PROGRESS.md` 为准。
- 锁定边界以 `DECISIONS.md` 为准。
- 单牌资料验收以 `CARD_DATA_STANDARD.md` 为准。
- 后续 AI 收到“开始任务”或“继续任务”时，按 `AGENTS.md` 执行。

任务 ID 前缀：

| 前缀 | 范围 |
|---|---|
| `DOC` | 文档、决策和流程 |
| `TQ` | 单牌资料质量与数据契约 |
| `QP` | 预设问题与问题配置 |
| `PO` | 牌位运算与牌阵适配 |
| `MR` | 多牌关系推理 |
| `CL` | 结论生成、评分与冲突消解 |
| `TX` | 模板化文本输出 |
| `AU` | 随机、历史和审计 |
| `EV` | 评测、测试和质量门禁 |
| `UI` | 界面接入与展示 |
| `REL` | 发布与稳定化 |

## 2. 阶段总览

| 阶段 | 名称 | 主要目标 |
|---|---|---|
| Phase 0 | 项目目标与任务系统 | 让任何后续 AI 能可靠接手 |
| Phase 1 | 单牌数据基础 | 建立 Schema、词典、黄金样本 |
| Phase 2 | 78 张牌资料升级 | 所有单牌资料达到 9.0+ |
| Phase 3 | 预设问题系统 | 建立覆盖主要场景的问题配置 |
| Phase 4 | 牌位运算系统 | 固定牌阵内部实现问题语义适配 |
| Phase 5 | 多牌关系引擎 | 从逐牌解释升级为关系推理 |
| Phase 6 | 结论与文本系统 | 结构化结论、冲突消解、模板渲染 |
| Phase 7 | 审计与历史升级 | 复现、版本、证据链和迁移 |
| Phase 8 | 评测与界面整合 | 达到三项 9.0+ 质量目标 |
| Phase 9 | 发布稳定化 | 回归、安全、性能、文档和发布 |

# Phase 1：单牌数据基础

## TQ-001 定义 CardSemanticProfile Schema

依赖：DOC-003

目标：

- 确定每张牌的正式数据结构
- 定义必填字段、枚举、数值范围和版本字段
- 选择实现方式：原生 JS 校验或 JSON Schema 等轻量方案

产物建议：

- `engine/card_schema.js`
- `engine/vocabularies.js`
- `tests/card_schema_test.js`

验收：

- 能校验一张完整样本
- 能拒绝缺字段、非法标签、越界数值和错误引用
- 不引入运行时大模型或网络依赖

## TQ-002 建立统一语义词典

依赖：TQ-001

目标：

定义并冻结第一版：

- 主题标签
- 关系标签
- 逆位机制
- 语义侧面
- 可计算维度
- 元素、数字、宫廷角色和阶段标签
- 禁止断言类别

产物建议：

- `engine/vocabularies.js`
- `docs/SEMANTIC_VOCABULARY.md`

验收：

- 同义标签被合并
- 每个标签有定义、适用范围和反例
- 测试可检查未注册标签

## TQ-003 制作 6 张黄金样本

依赖：TQ-002

牌目：

- 愚者
- 战车
- 隐者
- 高塔
- 圣杯二
- 星币八

目标：

- 验证 Schema 能表达不同牌型和主题
- 验证正逆位机制、领域适配和关系标签
- 形成后续 72 张牌的内容模板

产物建议：

- `engine/card_semantics.js` 或拆分数据文件
- `tests/card_golden_samples_test.js`

验收：

- 6 张全部通过 Schema
- 按资料标准人工评分均 ≥ 9.0
- 相似概念边界明确
- 六领域场景抽测通过

## TQ-004 建立资料评分与审查工具

依赖：TQ-003

目标：

- 自动统计字段覆盖、条目数量、重复率和非法标签
- 生成每张牌的质量报告
- 支持人工评分录入

产物建议：

- `scripts/audit_card_data.py` 或 JS 等价实现
- `tests/card_quality_gate_test.js`
- `.qa/card-quality-report.json`，是否提交由项目策略决定

验收：

- 能输出 100 分制评分明细
- 单项否决条件可自动识别
- 未达 90 分的牌无法通过质量门禁

# Phase 3：预设问题系统

## QP-001 设计问题分类与选择结构

依赖：DOC-002

目标：

在不允许自由文本的前提下，通过“领域 → 处境 → 询问角度”覆盖大多数常见场景。

验收：

- 不改变现有六大主题可见结构，除非用户另行决定
- 避免近义问题重复
- 每个问题都有明确意图和时间边界

## QP-002 建立 QuestionProfile Schema

依赖：QP-001、TQ-002

字段至少包括：

- 领域
- 问题意图
- 时间范围
- 必答维度
- 允许结论类型
- 禁止断言
- 风险等级
- 四牌阵适配配置

验收：

- 所有问题可被 Schema 校验
- 每个问题不再只靠分类 ID 解读

## QP-003 扩展并整理预设问题库

依赖：QP-002

建议规模：84–96 题。

目标分布可在任务中进一步校准：

- 感情与关系
- 事业与学业
- 财务与资源
- 自我成长
- 选择与决策
- 今日与短期指引

验收：

- 主要问题意图覆盖率 ≥ 95%
- 重复或高度近义问题率 ≤ 5%
- 高风险问题有明确禁止断言

## QP-004 为全部问题建立四牌阵适配

依赖：QP-003、PO-001

目标：

- 不改变牌位名称和结构
- 定义同一固定牌位在不同问题下的内部职责

验收：

- 每个问题支持四种牌阵
- 单张不会生成超出一张牌能力的完整因果报告
- 三、五、十张输出深度逐级增加

依赖：CL-002

- 建议可修正趋势

依赖：CL-003、QP-003

验收：

- 每类问题使用有限结论集合
- 不输出问题配置禁止的结论

依赖：CL-004

目标：

- 按结论类型和关系结构渲染
- 固定种子下可复现

依赖：TX-001

## TX-003 实现一致性与安全校验

依赖：TX-002

验收：

- 核心结论可追溯率 100%

## 3. 任务选择原则

后续 AI 只能选择：

1. `PROGRESS.md` 中的 `IN_PROGRESS` 任务
2. 没有进行中任务时选择唯一 `NEXT` 任务
3. 若任务被阻塞，先处理阻塞原因或记录为 `BLOCKED`

不得跳过 Schema、词典和黄金样本，直接批量重写 78 张牌。那种做法表面进度很快，之后会得到 78 种互不兼容的数据风格，十分符合人类传统的软件开发灾难流程，但本项目不采用。
