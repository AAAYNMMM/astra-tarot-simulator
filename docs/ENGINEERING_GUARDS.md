# 工程护栏与本地验证方案

## 1. 目的

本文档记录在模块化、纯规则引擎和资料升级之外必须同步建设的工程护栏。目标不是继续扩张产品功能，而是防止重构破坏、知识数据漂移、历史丢失、离线缓存遗漏和本地服务暴露内部文件。

本项目不使用 GitHub Actions。所有需要真实运行环境的测试、检查、构建和回归验证，统一复用 `AAAYNMMM/CWapi` 的本地 Runner 工作流。

## 2. CWapi 本地验证门禁

### 2.1 锁定规则

- 不创建、恢复、启用或依赖 `.github/workflows/`。
- GitHub 只保存源码、文档、配置、测试、轻量夹具、验证脚本和版本记录。
- 代码、数据、存储、缓存、启动器或发布相关变更，必须绑定完整 40 位 commit SHA 交给 CWapi Runner 验证。
- 没有与当前 commit 对应的 CWapi RESULT，不得宣称本地验证通过。
- GitHub 页面显示可合并、无冲突或代码审查通过，不能替代 CWapi 本地结果。
- 纯文档变更可以不运行完整回归，但必须完成文档一致性检查。

### 2.2 项目侧职责

星纱塔罗仓库需要提供可由 CWapi 执行的确定性验证入口，建议最终建立：

```text
automation/
├── validate.py
├── browser_smoke.py
└── README.md
```

`automation/validate.py` 应按阶段逐步覆盖：

1. 确认实际 commit 与目标 commit 一致。
2. 检查 Git 工作区前后状态。
3. 运行 Python 单元测试。
4. 运行 Node 数据、模块和规则测试。
5. 运行模块行数与依赖方向检查。
6. 运行知识目录、注册表和动态导入完整性检查。
7. 检查生成文件是否与源数据一致。
8. 运行 Doctor。
9. 必要时运行浏览器冒烟或完整回归。
10. 输出机器可读摘要并返回可靠退出码。

脚本不得修改仓库源码，不得依赖人工交互，不得把大型日志或浏览器产物提交到 GitHub。

### 2.3 建议验证组合

普通 JavaScript、Python、数据或样式变更：

```text
git_rev_parse
git_status
repository_automation: automation/validate.py --scope targeted
repository_automation: automation/validate.py --scope full
collect_hashes
git_status
```

发布候选还必须增加浏览器回归、离线检查、历史迁移与缓存检查。

## 3. 本地服务器访问边界

当前 Python 静态服务器以仓库根目录为服务目录。后续必须限制浏览器可访问范围。

目标规则：

- 仅允许访问应用入口、`src/`、`assets/`、manifest、图标和必要 PWA 文件。
- 明确拒绝 `.git/`、`.github/`、`docs/`、`tests/`、`scripts/`、`automation/`、`.qa/`、隐藏文件和临时文件。
- 默认只监听 `127.0.0.1`。
- 用户显式选择非本机监听地址时必须显示安全警告。
- 生命周期接口只接受本应用页面发出的同源请求。
- 生命周期接口使用启动时随机令牌，避免其他本地网页伪造打开、关闭或事件连接请求。
- 增加适合原生 ES Modules 的 Content Security Policy。
- 文件访问边界必须有自动测试。

不要求新建构建产物目录。优先通过请求处理器白名单保持 `python run.py` 直接运行。

## 4. 可测试随机接口

生产抽牌继续使用高质量系统随机源，但核心逻辑不得直接绑定浏览器全局随机函数。

目标接口：

```js
createReading({
  deck,
  spread,
  randomSource,
});
```

要求：

- 生产环境注入安全随机源。
- 测试环境可以注入固定随机源或固定种子。
- 问题与牌义加载不得影响抽牌顺序和正逆位。
- 重构前后的算法行为可以用固定输入比较。
- 后续可复现随机算法与审计种子在 `AU-001` 完成。

模块化阶段只建立依赖边界，不提前改变现有随机分布。

## 5. 静态知识单一来源与生成文件

人工维护的主要来源是：

- 单张 `CardSemanticProfile`
- 单题 `QuestionProfile`
- 固定牌阵定义与关系图
- 语义词典
- 文本模板

下列内容应由脚本生成，避免同一 ID、路径或名称被人工维护多次：

- 轻量卡牌目录
- 卡牌动态导入注册表
- 轻量问题目录
- 问题动态导入注册表
- knowledge 完整性清单
- PWA 预缓存清单

生成要求：

- 生成脚本位于 `scripts/`。
- 生成结果位于 `src/generated/` 或明确的 generated 文件。
- 文件头记录生成脚本和命令。
- 生成结果提交仓库，用户启动时不运行生成脚本。
- 验证脚本必须检查生成结果是否过期。
- 不允许人工直接修改生成文件。

## 6. 单牌资料来源与审校

单牌资料达到 9.0 以上不仅要求字段丰富，还必须有来源、边界和交叉审查。

### 6.1 来源记录

每张牌在开发数据中应记录：

- 主要传统体系
- 使用的参考资料 ID
- 相关章节或牌目
- 项目现代化解释部分
- 审查状态
- 最近审查日期

建立：

```text
docs/references/
├── bibliography.md
├── interpretation-policy.md
└── source-conflict-policy.md
```

禁止把来源不明的网络牌义直接当成正式资料。

### 6.2 跨牌一致性

资料审查必须检查：

- 近义牌之间是否有明确边界
- 同花色数字发展是否连续
- 宫廷牌跨花色与同花色层级是否区分
- 大阿卡纳阶段是否连贯
- 正逆位是否只是机械正反词替换
- 主题和建议是否大面积重复

建议支持：

```js
semanticNeighbors: {
  similar: [],
  contrastedWith: [],
  developsFrom: [],
  developsToward: [],
}
```

### 6.3 反例测试

每张牌必须同时定义常见误读和禁止推断。测试集应包含故意错误的解释候选，验证系统能够拒绝：

- 无依据的具体事件
- 必然成功或失败
- 强制人物指认
- 精确日期
- 医疗、法律和投资确定性判断
- 只依赖单个关键词的机械解释

## 7. 历史备份与容量策略

IndexedDB 不能被当作永久备份。后续历史系统必须支持：

- 导出全部历史为带 Schema 版本的 JSON
- 导出单条历史
- 导入前结构、版本和大小验证
- 导入前预览记录数量
- 重复 ID 与冲突处理
- 完整导出与仅显示结果导出两种模式
- 导入失败不破坏现有数据

容量策略：

- 不再使用静默 `slice` 删除记录。
- 默认容量在实现任务中通过真实记录大小确定，初始建议上限 500 条完整记录。
- 接近浏览器存储配额时明确提醒。
- 支持按日期、问题、牌阵筛选和批量删除。
- 自动清理必须获得用户明确授权。

## 8. Doctor 与浏览器回归

### 8.1 Doctor

最终提供：

```text
python scripts/doctor.py
```

Doctor 至少检查：

- Python 版本和启动器基础条件
- 必要入口文件
- 四套牌面与牌背完整性
- 卡牌目录、详细资料和注册表一致性
- 问题目录与 QuestionProfile 一致性
- 四种牌阵和牌位未改变
- 动态导入路径存在
- 生成缓存清单未过期
- 模块行数与依赖边界
- 历史 Schema 与迁移版本
- LICENSE 与第三方来源文档

输出统一 `PASS / WARN / FAIL`，失败时使用非零退出码。

### 8.2 浏览器回归

至少覆盖：

- 启动与准备页
- 主题、问题、牌阵和牌面选择
- 洗牌与发牌
- 单张和全部翻牌
- 生成结果
- 历史写入、读取和删除
- 页面刷新
- 生命周期连接与关闭
- 离线重新打开
- 动态加载抽中卡牌和问题资料
- IndexedDB 不可用时的降级

浏览器回归由 CWapi 在本地真实环境运行，不通过 GitHub Actions 执行。

## 9. 许可证与第三方声明

发布前必须建立：

```text
LICENSE
THIRD_PARTY_NOTICES.md
```

分别说明：

- 项目源代码许可证
- 四套牌面的来源和许可状态
- 公共领域资源
- 项目原创内容
- 外部脚本或素材的许可证

README 中的来源链接不能替代项目级许可证。

## 11. 明确不做

当前不增加：

- GitHub Actions
- 图数据库
- 后端 SQLite
- 用户账户和云同步
- 插件系统
- 自定义牌阵
- 自由文本问题
- 强制 npm 构建链

项目应先把现有离线产品做成可维护、可验证、可恢复的可靠系统，而不是在地基尚未验收时宣布建设生态平台。
