# 项目决策记录

本文档保存已经确认的产品与技术决策。后续开发不得仅凭临时偏好推翻这些决策。若用户明确改变方向，应在本文档新增一条带日期的变更记录，并同步调整路线图和进度。

## D-001：运行时采用纯规则算法

**状态：锁定**

- 解牌运行时不得调用 AI 大模型、在线推理 API 或云端生成式服务。
- 所有牌义筛选、牌位转换、牌间关系、结论选择、冲突消解和文本输出均由确定性规则完成。
- 可以在开发阶段由人或 AI 协助编写资料与代码，但最终运行产物必须离线、可审计、可测试。

## D-002：只允许固定预设问题

**状态：锁定**

- 不提供自由文本问题解析。
- 问题库通过领域、处境和询问角度覆盖大多数常见场景。
- 每个问题必须拥有独立 `QuestionProfile`，不能只依赖六个粗粒度分类。
- 问题配置必须声明回答维度、允许结论、禁止断言、时间范围和四种牌阵的语义适配。

## D-003：四种牌阵不得改变

**状态：锁定**

保留以下四种牌阵及其现有牌位结构：

1. 心语单张，1 张
2. 时间之流，3 张
3. 五牌十字，5 张
4. 凯尔特十字，10 张

不得新增、删除、重命名或重新排列牌位。优化只能发生在：

- 问题对牌位的语义映射
- 牌位运算符
- 固定牌位关系图
- 多牌关系与结论算法
- 输出结构与文字模板

## D-004：抽牌与解读严格分离

**状态：锁定**

- 抽牌先完成，解读后进行。
- 问题、牌义或期望结果不得影响抽中的牌。
- 不允许为了生成更连贯的结论进行隐藏重抽、替换或调整正逆位。
- 后续应保存随机种子、抽牌顺序、正逆位结果和引擎版本，以支持复现和审计。

## D-005：三项核心质量目标均为 9.0/10 以上

**状态：锁定**

目标包括：

1. 单牌资料质量 ≥ 9.0
2. 多牌综合能力 ≥ 9.0
3. 预设问题贴合度 ≥ 9.0

这些分数必须通过明确量表和测试集评估，不能由开发者凭感觉自评。

“可靠”在本项目中表示：

- 牌义资料完整且内部一致
- 结论与问题、牌位和牌面证据一致
- 同一输入能够复现
- 冲突和不确定性被正确表达
- 不做无证据的确定性断言

项目不宣称科学验证的超自然预测准确率。

## D-006：单牌资料必须结构化

**状态：锁定**

每张牌不得只包含关键词、正位段落、逆位段落和一句建议。必须具备可供算法使用的结构化资料，包括但不限于：

- 核心主题
- 原型与传统象征
- 正位与逆位机制
- 状态、原因、阻碍、机会、行动、趋势等语义侧面
- 领域适配
- 强度、速度、稳定性、主动性等可计算维度
- 元素、数字、宫廷角色或大阿卡纳阶段属性
- 禁止误读和边界说明

详细标准见 `CARD_DATA_STANDARD.md`。

## D-007：牌位是运算符，不是提示文字

**状态：锁定**

牌位必须改变语义选择、时态、权重和结论职责。例如同一张牌落在“挑战”“建议”“结果”时必须产生不同的计算路径，不能只在同一段牌义前加一个牌位名称。

## D-008：先生成结构化结论，再渲染文字

**状态：锁定**

解读流程必须先生成包含证据、反证、条件、置信度和结论类别的结构化对象，再由模板渲染成自然语言。

不得直接把每张牌的说明段落依次拼接成综合解读。

## D-009：关键牌位高于正逆位数量

**状态：锁定**

- 不允许用正位数量与逆位数量直接决定整体积极或消极。
- 不允许以“逆位占多数”作为主要标题选择逻辑。
- 关键牌位、问题维度匹配、牌义强度、关系支持和冲突修正应共同决定结论。

## D-010：大阿卡纳不作为第五花色元素

**状态：锁定**

- 大阿卡纳应独立分析其原型、阶段和关键位置权重。
- 不得把全部 22 张大阿卡纳统一归为“灵元素”后与四个 14 张花色直接比较优势，否则统计天然偏斜。

## D-011：冲突必须解释

**状态：锁定**

当牌面出现相反方向时，规则引擎依次尝试：

1. 区分内在与外在
2. 区分当前与未来
3. 区分动机与条件
4. 判断建议是否修正趋势
5. 转化为条件分支
6. 无法整合时明确输出趋势分散

不得悄悄丢弃不利于主结论的牌。

## D-012：保持轻量、离线和可维护

**状态：锁定**

当前阶段优先使用：

- 原生 JavaScript
- Python 标准库
- JavaScript 数据模块
- 浏览器原生 IndexedDB 与 localStorage
- Node 与 Python 测试

除非现有方案明确无法满足性能或维护需求，否则不引入大型规则平台、图数据库、云服务或复杂构建链。

## D-013：代码必须模块化并适合 GitHub 精确修改

**状态：锁定**

- 在新规则引擎开发前，先完成 `MOD-001` 至 `MOD-006`。
- `app.js`、`styles.css` 和 `data.js` 必须拆分为职责清楚的小模块。
- JavaScript 人工维护文件不得超过 600 行，超过 450 行应主动检查拆分。
- CSS 人工维护文件不得超过 900 行，超过 700 行应主动检查拆分。
- 应用入口建议不超过 200 行。
- 不得通过建立另一个超大文件来假装完成模块化。
- 每个模块应有明确依赖方向，禁止循环依赖。
- `engine/` 不得依赖 DOM，知识数据模块不得依赖 UI、存储或运行状态。
- 所有后续任务必须运行模块规模检查。

具体目录、拆分顺序和验收标准见 `MODULARIZATION_PLAN.md`。

## D-014：单牌资料采用一张牌一个模块

**状态：锁定**

- 每张完整 `CardSemanticProfile` 独立保存为一个 JavaScript 数据模块。
- 大阿卡纳和四个花色通过轻量目录和注册表加载。
- 索引文件只能负责导入、导出、目录或加载映射，不得重新塞入大段单牌资料。
- 修改单张牌时，应主要只影响该牌模块、对应测试和必要索引。
- 抽牌使用轻量卡牌目录，详细资料是否已加载不得影响抽牌结果。

## D-015：模块化不引入强制构建步骤

**状态：锁定**

- JavaScript 使用浏览器原生 ES Modules。
- 项目继续通过 `python run.py` 直接运行。
- 不要求用户安装 npm 依赖或先执行构建命令。
- CSS 可通过模块入口和分文件导入组织。
- service worker 必须显式覆盖新增模块，保持完整离线能力。
- 开发阶段可以运行 Python 生成脚本，但生成结果必须提交仓库，用户启动时不需要运行脚本。

## D-016：可执行源代码统一放入 src

**状态：锁定**

- 应用代码、规则引擎、静态知识、存储适配和样式统一放入 `src/`。
- 仓库根目录只保留启动入口、PWA 根文件、资源、测试、脚本和文档。
- 不再在仓库根目录继续新增业务 JavaScript 或大型 CSS 文件。
- `assets/` 只保存二进制或媒体资源，不保存规则数据。

## D-017：静态知识与用户数据必须分离

**状态：锁定**

- 卡牌、问题、牌阵、词典和模板属于只读静态知识，放入 `src/knowledge/`。
- 页面选择、翻牌和动画属于临时状态，不能写回静态知识对象。
- 用户设置和历史属于本地持久数据，放入 `src/storage/` 所定义的接口。
- `engine/` 只能读取传入的知识和输入，不得自行访问浏览器存储。

完整分层见 `DATA_ARCHITECTURE.md`。

## D-018：详细卡牌和问题资料按需加载

**状态：锁定**

- 卡牌和问题分别提供轻量目录，用于选择、抽牌和基础展示。
- 完整 `CardSemanticProfile` 和 `QuestionProfile` 通过注册表动态导入。
- 一次占卜只加载实际抽中的牌和当前问题的详细资料。
- 注册表必须缓存已加载模块，并接受完整性测试。
- 加载失败不得重抽、替换牌或悄悄使用错误资料。

## D-019：设置与历史采用分层存储

**状态：锁定**

- `localStorage` 只保存小型同步设置。
- 完整占卜历史、证据链和版本信息使用原生 IndexedDB。
- 控制器只依赖统一 `readingStore` 和 `settingsStore` 接口，不得直接调用底层 API。
- IndexedDB 不可用时允许精简历史降级，但不能阻断占卜和解读。

## D-020：历史保存结果快照，不复制知识库

**状态：锁定**

每条历史必须保存：

- 问题、牌阵和牌面 ID
- 必要显示快照
- 随机种子与抽牌结果
- 本次使用的引擎和资料版本
- Observation、Relation、Claim、校验结果和渲染文本

不得把 78 张完整牌资料、全部问题库或所有模板复制进每条历史。

## D-021：缓存清单由脚本生成并按组管理

**状态：锁定**

- 模块化后使用开发脚本生成 PWA 预缓存清单，并将生成文件提交仓库。
- 缓存至少区分 shell、knowledge 和四套牌面资源组。
- 单个资源失败不得导致全部缓存安装失败。
- 动态导入的卡牌和问题资料必须进入 knowledge 缓存与完整性检查。
- 用户启动项目时不需要执行缓存生成脚本。
